# PRD：持仓新闻事件雷达

## 一句话定位

基于用户当前持仓和关注标的，自动发现与持仓高度相关的公告、监管申报、新闻和事件日，并生成低噪音、可追溯、可解释的风险提醒。

这个产品不是通用新闻流。它的目标是回答：

```text
我现在持有的股票，最近有没有足以影响仓位判断的事件？
```

第一版重点覆盖高信噪比事件：减持、拟减持、限售/lock-up 到期、增发、重大公告、业绩预告、财报日、公司行动和监管申报。

## 背景

当前系统已经接入：

- 富途实时持仓。
- 富途历史成交和账户快照。
- 个股研究、知识库、用户心得和周复盘。
- 港股 IPO 列表。

当前缺口：

- 周复盘和持仓分析明确没有接入外部新闻/公告事件源。
- 用户需要知道“持仓相关”的风险事件，而不是每天阅读大量财经新闻。
- 富途 App 内有部分资讯和事件日，但 Futu OpenAPI 目前更适合作为持仓/行情来源，不应被假设为新闻和公告源。

## 典型样例：AXTI Lock-up 到期

用户观察到 AXTI 在富途 App 中出现 2026-06-21 / 2026-06-22 附近的 lock-up 到期提示，同时股票在事件前出现明显下跌和放量。

第一版系统应该能合成以下事实：

| 类型 | 事实 | 来源 |
| --- | --- | --- |
| 官方发行事实 | AXT 于 2026-04-22 宣布完成公开发行 8,560,311 股，发行价 64.25 美元，募资约 5.5 亿美元 | Business Wire |
| SEC 发行文件 | 2026-04-21 424B5 写明发行 8,560,311 股，并授予承销商最多 1,284,046 股超额配售权 | SEC 424B5 |
| SEC 锁定期条款 | 424B5 / 8-K 显示董事、高管和公司相关 lock-up 自 prospectus supplement 日期后持续 60 天 | SEC 424B5 / 8-K |
| 推导事件日 | 2026-04-21 + 60 天 = 2026-06-20；周末后第一个美股交易日为 2026-06-22 | 系统推导 |
| 媒体标签 | 部分媒体/数据平台表述为约 8.6M share lockup expiration on 2026-06-21 | 媒体/数据平台 |

系统不应该简单输出“AXTI 有新闻”。它应该输出：

```text
AXTI - Lock-up 到期 / 增发后潜在抛压

事件日：
- 合同/日历口径：2026-06-20 / 2026-06-21
- 下一交易日口径：2026-06-22

为什么重要：
- 4 月公开发行规模为 8,560,311 股，约占当前流通股的重要比例。
- 董事、高管和公司存在 60 天 lock-up 条款。
- 近期股价波动和成交量放大，事件更容易被市场交易。

证据：
- SEC 424B5：发行规模、发行价、lock-up 条款。
- SEC 8-K：承销协议和 lock-up agreement。
- Business Wire：公开发行完成公告。
- 媒体口径：将其标记为 8.6M share lockup expiration。

注意：
- SEC 原文确认发行规模和 lock-up 条款，但不应机械表述为“8.56M 股全部在 6/21 可卖”。
- 媒体口径需要保留来源和置信度。
```

## 产品原则

### 1. 持仓相关优先

只主动推送与以下标的相关的事件：

- 当前持仓。
- 最近 30 天交易过的标的。
- 用户明确加入观察名单的标的。
- 用户最近主动询问或研究过的标的。

默认不做全市场新闻流。

### 2. 官方事实优先，媒体标签辅助

事件卡必须区分：

- 官方原始事实：SEC、HKEXnews、交易所公告、公司 IR、Business Wire 等。
- 媒体/数据平台标签：TheFly、Sahm Capital、Perplexity Finance、TipRanks、财经媒体等。
- 系统推导：日期计算、规模占比、持仓相关性、事件优先级。

系统可以使用媒体标题发现事件，但不能让媒体标题覆盖官方文件。

### 3. 不把相关性说成因果

系统可以说：

```text
事件可能加剧市场对抛压的担忧。
```

不能说：

```text
股价下跌就是因为这条事件。
```

除非有官方解释或极强证据。

### 4. 低噪音

第一版不推送普通新闻、重复转载、无持仓关系的宏观新闻、没有新事实的短讯。

系统宁可漏掉低价值新闻，也不要每天制造信息负担。

## 用户场景

### 场景 1：每日持仓事件雷达

触发方式：

```text
持仓事件
今日持仓新闻
风险雷达
```

输出：

```text
持仓事件雷达 2026-06-20

高优先级
1. AXTI - Lock-up 到期 / 增发后潜在抛压
   事件日：2026-06-21，下一交易日 2026-06-22
   证据：SEC 424B5 / 8-K，Business Wire，媒体事件标签
   为什么重要：发行规模约 8.56M 股，存在 60 天 lock-up，近期放量下跌
   下一步：观察事件日前后成交量、关键价位和是否出现新增 Form 4 / 144

中优先级
2. XXX - 业绩预告 / 财报日临近
3. XXX - 港股配售公告
```

### 场景 2：单票事件追问

用户输入：

```text
AXTI 最近有什么重要新闻？
```

系统输出：

```text
AXTI 最近最重要的不是普通新闻，而是 lock-up 到期和内部人交易组合事件。

1. 2026-06-21 / 2026-06-22：lock-up 到期
2. 2026-06-17：Form 4 内部人卖出披露
3. 2026-06-08：Form 144 拟出售披露
4. 2026-04-22：公开发行完成，发行 8,560,311 股
```

### 场景 3：周复盘事件归因

周复盘中，系统将事件作为“原因候选”，而不是确定因果。

```text
AXTI 本周出现明显回撤。事件层面，4 月公开发行后的 60 天 lock-up 到期临近，且近期有 Form 4 / Form 144 披露。该组合可能强化了市场对短期供应和获利盘的担忧。
```

## P1 范围

### 覆盖市场

第一版优先覆盖：

| 市场 | 数据源 | 事件类型 |
| --- | --- | --- |
| 美股 | SEC EDGAR submissions / companyfacts / filing documents | Form 4、Form 144、8-K、424B5、S-3、S-8、13D/13G |
| 港股 | HKEXnews | 配售、认购、减持、盈利警告、财报、重大公告 |
| A 股 | 暂缓或调研 | 减持计划、限售解禁、业绩预告、交易所问询 |

### P1 事件类型

| 事件 | 优先级 | 说明 |
| --- | --- | --- |
| lock-up / 限售到期 | 高 | 需要结合发行文件、锁定期条款和交易日推导 |
| Form 144 拟出售 | 高 | 结构化字段较好，适合直接解析 |
| Form 4 实际卖出 | 高 | 需要区分卖出、授予、期权行权、自动计划 |
| 增发 / 公开发行 / shelf registration | 高 | 稀释和潜在供应事件 |
| 8-K 重大事项 | 中高 | 需要摘要分类，避免所有 8-K 都高优先级 |
| 港股配售/认购/减持公告 | 高 | 需要 HKEXnews 分类和关键词抽取 |
| 财报日/业绩预告 | 中 | 作为日历事件和波动风险 |

P1 不做：

- 社交媒体情绪监控。
- 全市场新闻热榜。
- 自动交易建议。
- 复杂技术面分析。
- 期权链和隐含波动率分析。

## 数据源设计

### SEC

用途：

- 通过 ticker -> CIK 映射定位公司。
- 读取 `data.sec.gov/submissions/CIKxxxx.json` 获取近期 filing。
- 对重点 filing 下载原始 XML/HTML。
- 解析结构化字段和关键条款。

重点解析：

- `Form 144`：拟售人、关系、拟售股数、拟售日期、市场价值、notice date。
- `Form 4`：报告人、交易日期、交易代码、股数、价格、剩余持股、10b5-1 标记。
- `424B5 / S-3 / 8-K`：发行规模、发行价、超额配售、lock-up 条款、承销协议。

### 公司新闻稿 / Business Wire

用途：

- 验证公司主动公告。
- 补全发行完成、募资用途、会议安排、财报发布等事实。

### 媒体和数据平台

用途：

- 发现官方文件中不易直接检索的事件标签。
- 提供市场关注点。

要求：

- 必须保留来源。
- 必须标注“媒体口径”。
- 不允许静默覆盖官方事实。

### 富途

用途：

- 当前持仓。
- 持仓权重。
- 当前盈亏。
- 行情快照和成交量，如果 OpenAPI 权限可用。

富途不作为 P1 新闻源的唯一依赖。

## 工程落地数据源清单

P1 必须先接能稳定脚本化访问的数据源，媒体和模型摘要作为增强层。

| 数据源 | 获取方式 | P1 用途 | 是否必需 | 备注 |
| --- | --- | --- | --- | --- |
| 富途当前持仓 | 既有 `get_futu_positions()` / MCP `get_realtime_portfolio_positions` | 确定扫描 universe、持仓相关度、仓位权重 | 必需 | 只读，不下单 |
| SEC ticker-CIK mapping | `https://www.sec.gov/files/company_tickers.json` | 美股 ticker -> CIK | 必需 | 可每日缓存 |
| SEC submissions JSON | `https://data.sec.gov/submissions/CIK##########.json` | 发现近期 filing | 必需 | P1 美股主入口 |
| SEC Archives filing document | `https://www.sec.gov/Archives/edgar/data/...` | 解析 Form 4、144、8-K、424B5 原文 | 必需 | 需要保存原文快照或摘要 hash |
| Business Wire / 公司 IR | RSS、页面抓取、新闻稿 URL | 验证公司公告和发行完成 | P1 可选、P2 增强 | 第一版可先通过 SEC 附件和人工 URL 补充 |
| HKEXnews | 既有 official source 能力或新增公告搜索 | 港股公告事件 | P1 可选 | 美股跑通后补 |
| 媒体/数据平台 | 搜索、RSS、网页抓取、人工输入 URL | 事件标签发现 | P1 可选 | 只做标签，不做最终事实源 |
| 行情/成交量 | 富途行情快照或后续技术面 Agent | 事件影响评估 | 不在本 PRD 展开 | 本模块只传递事件规模和日期 |

第一版工程不需要等待所有源齐全。最小闭环是：

```text
富途持仓 -> 美股 ticker -> SEC submissions -> 解析重点 filing -> 生成事件卡 -> 命令输出
```

AXTI 的 P1 验收样例：

```text
AXTI -> CIK 0001051627
-> 2026-04-21 / 2026-04-22 424B5、8-K、Business Wire
-> 识别 8,560,311 股发行、64.25 美元发行价、60 天 lock-up
-> 推导 2026-06-20 / 2026-06-22 事件日
-> 输出 lock-up 到期事件卡
```

## 脚本、云端 Codex 和模型分工

### 脚本负责

脚本负责所有可验证、可重复、需要入库的事实。

| 任务 | 脚本职责 |
| --- | --- |
| 持仓 universe | 从富途读取当前持仓、近期交易、观察名单 |
| 代码映射 | ticker -> CIK、市场代码标准化 |
| Filing 发现 | 拉取 submissions JSON，筛选 filing type 和日期 |
| 原文抓取 | 下载 SEC XML/HTML、公司公告页面、必要附件 |
| 结构化解析 | Form 4 / 144 XML 字段、发行股数、发行价、日期、交易代码 |
| 时间推导 | lock-up 起始日 + 天数、下一交易日、事件窗口 |
| 去重 | canonical event key、source hash、URL 归并 |
| 优先级初筛 | 持仓命中、事件类型、事件时间、规模字段 |
| 持久化 | 写入事件、来源、证据、抓取状态 |

脚本输出必须是结构化 JSON，不让模型决定事实是否存在。

### 云端 Codex 负责

需要“像研究员一样补资料、读长文件、判断哪些来源值得沉淀”的任务，默认走云端 Codex worker，而不是本地 Codex desktop。

项目既有约束：

```text
Codex desktop / Mac 只作为控制面：
- 可以编辑代码。
- 可以创建云端任务。
- 可以查询云端任务状态。
- 可以审阅云端产物。
- 可以运行不触发真实研究的本地测试。

真实股票研究、source collection、draft enrichment、audit/review generation，
默认由云服务器上的 worker 执行。
```

事件雷达中适合交给云端 Codex worker 的任务：

| 任务 | 为什么交给 Codex worker |
| --- | --- |
| 复杂 8-K / 424B5 / S-3 长文本阅读 | 条款位置不固定，脚本初期难以完整覆盖 |
| lock-up 条款发现和解释 | 需要结合承销协议、招股书、新闻稿和交易日 |
| 媒体标签与官方文件对齐 | 需要判断媒体说法是否能被官方文件支持 |
| 新市场/新事件类型探索 | 例如 A 股限售解禁、港股减持公告规则尚未稳定 |
| provider backlog 生成 | 记录哪些解析能力值得沉淀成脚本 |

P1 执行方式：

```text
脚本发现候选 source
-> 如果规则能解析，直接生成事件
-> 如果需要复杂理解，创建云端 Codex event research job
-> 云端 worker 产出结构化 event packet
-> 脚本校验并入库
```

这与既有 research job 方向保持一致：

```text
provider = codex
execution_location = cloud_worker
```

### 普通模型负责

普通模型只处理轻量的“理解、摘要和分类”，不负责创造事实。对于可异步、可审计、资料发现型任务，优先使用云端 Codex worker。

| 任务 | 模型职责 | 输入约束 |
| --- | --- | --- |
| 8-K / 424B5 文本分类 | 判断是增发、lock-up、会议、经营更新、普通行政事项 | 只读脚本抓取的原文片段 |
| 条款摘要 | 将 lock-up、发行、超额配售条款转成中文摘要 | 必须引用 source fact |
| 媒体标签归并 | 将多篇媒体短讯归并为一个事件标签 | 不覆盖官方字段 |
| 用户可读输出 | 生成事件卡解释和“为什么重要” | 只能基于结构化 facts |
| 不确定性说明 | 标出“媒体口径”和“官方文件未直接说明”的差异 | 必须保留置信度 |

模型禁止：

- 编造事件日期。
- 编造股数、价格、交易人。
- 把股价变化写成确定因果。
- 静默把媒体标题当成官方事实。

### 推荐流水线

```text
1. 脚本发现来源
2. 脚本提取硬字段
3. 模型辅助分类和摘要
4. 脚本校验必填字段
5. 脚本入库
6. 模型生成用户可读事件卡
```

如果步骤 3 涉及补充资料、长文档研究、跨来源核验，应替换为：

```text
3. 创建云端 Codex worker 任务
4. 云端 worker 输出 event packet 和 source audit
5. 脚本校验必填字段
6. 脚本入库
7. 模型或模板生成用户可读事件卡
```

## 持久化设计

持久化目标不是保存所有新闻，而是保存“可复用的事件事实”和“用户当时看到的提醒”。

建议新增三层数据：

### 1. 原始来源层：`event_sources`

保存抓取到的来源和审计信息。

关键字段：

| 字段 | 说明 |
| --- | --- |
| `id` | source id |
| `source_type` | `sec_filing` / `press_release` / `media` / `hkex_announcement` |
| `publisher` | SEC、Business Wire、HKEXnews、Sahm Capital 等 |
| `url` | 原始 URL |
| `title` | 来源标题 |
| `published_at` | 发布时间或 filing date |
| `accession_number` | SEC filing 适用 |
| `form_type` | SEC filing type |
| `raw_hash` | 原文 hash，用于去重和变更检测 |
| `fetched_at` | 抓取时间 |
| `fetch_status` | ok / failed / partial |

原文全文不一定全部入库。P1 可以保存 URL、hash、关键 excerpt 和解析后的 source facts；如果后续需要离线审计，再增加对象存储或本地归档。

### 2. 事件事实层：`portfolio_events`

保存归一化后的事件。

关键字段：

| 字段 | 说明 |
| --- | --- |
| `id` | event id |
| `market` / `symbol` | 标的 |
| `event_type` | lockup_expiration、form_144_sale_notice、insider_sale、offering、earnings 等 |
| `event_title` | 归一化标题 |
| `event_date` | 合同/公告口径事件日 |
| `next_trading_date` | 下一交易日 |
| `detected_at` | 系统首次识别时间 |
| `priority` | high / medium / low |
| `confidence` | high / medium / low |
| `status` | upcoming / active / recent / archived |
| `source_ids` | 关联来源 |
| `source_facts` | JSONB，硬事实 |
| `derived_facts` | JSONB，系统推导 |
| `media_labels` | JSONB，媒体口径 |
| `uncertainties` | JSONB，不确定点 |
| `dedupe_key` | 去重键 |

推荐去重键：

```text
market + symbol + event_type + event_date + primary_source_accession_or_url
```

AXTI lock-up 这类多来源事件，需要允许多个 source 合并到同一个 `portfolio_events`。

### 3. 提醒快照层：`event_alerts`

保存“哪天给用户看过什么”，避免重复打扰，也方便周复盘引用。

关键字段：

| 字段 | 说明 |
| --- | --- |
| `id` | alert id |
| `event_id` | 关联事件 |
| `alert_date` | 提醒日期 |
| `channel` | dingtalk / cli / web |
| `alert_level` | high / medium / low |
| `rendered_summary` | 当时展示给用户的摘要 |
| `user_action` | ignored / opened / asked_followup / confirmed_relevant |

### 与现有知识库的关系

- `event_sources` 可以复用现有 `sources` 设计理念，但事件源需要更强的抓取状态、hash 和 SEC 字段。
- `portfolio_events` 不等于用户心得，不自动写入 user insight。
- 只有当用户明确说“记住这个教训/心得”，才进入候选心得或正式心得。
- 周复盘引用事件时，从 `portfolio_events` 和 `event_alerts` 读取，不重新抓全量新闻。

## 查询时间跨度设计

不同事件的“发现窗口”和“展示窗口”不同，不能统一写死为 30 天。

### 默认扫描窗口

| 查询类型 | 回看窗口 | 前瞻窗口 | 说明 |
| --- | ---: | ---: | --- |
| 每日持仓事件扫描 | 30 天 | 14 天 | 覆盖近期 filing 和临近事件日 |
| 单票事件查询 | 90 天 | 30 天 | 用户主动问时给更完整上下文 |
| 周复盘 | 14 天 | 14 天 | 覆盖本周发生和下周将发生 |
| 新持仓首次扫描 | 180 天 | 30 天 | 防止刚买入时漏掉历史增发/lock-up |
| lock-up / 限售事件推导 | 365 天 | 180 天 | 需要从较早发行文件推导未来事件日 |
| Form 4 / Form 144 | 30 天 | 0 天 | 主要是披露后事件，通常不需要长前瞻 |
| 财报/会议日历 | 30 天 | 45 天 | 财报日有明确未来窗口 |

### 为什么 lock-up 要长窗口

AXTI 说明：6 月事件来自 4 月发行文件，只有 60 天间隔。其他公司可能有 90 天、180 天或更长锁定期。

因此 lock-up 不能只查最近 30 天 filing。P1 规则：

```text
如果当前持仓存在 365 天内的 offering / IPO / resale registration / underwriting agreement，
就尝试解析 lock-up 条款并生成未来 180 天事件。
```

### 展示窗口

每日摘要默认展示：

- 未来 7 天将发生的高优先级事件。
- 过去 3 天刚披露的高优先级事件。
- 过去 14 天披露但尚未过事件日的 lock-up / 财报 / 会议事件。

单票详情默认展示：

- 过去 90 天事件时间线。
- 未来 30 天已知事件日。
- 如果命中发行/lock-up 文件，可回溯到 365 天内的源文件。

### 归档规则

- 事件日后 14 天无新增 source，状态转为 `archived`。
- lock-up、增发、重大监管事项可保留在周复盘引用池 90 天。
- 低优先级媒体新闻 30 天后默认不展示，除非已关联到高优先级事件。

## 运行成本、调度频率和去重策略

### 单次运行成本

成本分为脚本抓取成本、云端 Codex / 模型成本和用户注意力成本。

### 脚本抓取成本

P1 默认只扫描当前持仓和近期交易标的，通常是几十只以内。美股 SEC 源的脚本成本很低：

```text
每只美股：
1 次 ticker -> CIK 映射缓存读取
1 次 submissions JSON 拉取或缓存命中
0-N 次重点 filing 原文下载
```

粗略估计：

| 场景 | 网络请求量 | 说明 |
| --- | ---: | --- |
| 每日增量扫描 20 只美股 | 20-80 次 | 只下载新 filing 和重点 filing |
| 新持仓首次扫描 1 只 | 5-30 次 | 可能回看 365 天 offering / lock-up 文件 |
| 单票详情查询 | 5-50 次 | 取决于是否已有缓存 |

只要做缓存和增量扫描，脚本运行成本接近 0，主要受 SEC 请求频率和网络稳定性约束。

### 云端 Codex / 模型成本

Codex / 模型不参与全量抓取，只处理候选事件。

P1 规则：

- submissions 筛选、Form 4 / 144 XML 解析，不调用 Codex / 模型。
- 只有 `8-K`、`424B5`、`S-3`、长公告、媒体短讯归并等需要语义理解时才调用 Codex / 模型。
- 如果需要补资料、跨来源核验或 source audit，优先创建云端 Codex worker 任务。
- 已经解析过且原文 hash 未变化的 source，不重复调用 Codex / 模型。

粗略估计：

| 运行类型 | Codex / 模型调用量 | 说明 |
| --- | ---: | --- |
| 每日无新增重要 filing | 0 次 | 只做脚本扫描 |
| 每日少量新增 filing | 0-5 次 | 只摘要候选事件；复杂项进云端 Codex 队列 |
| 新持仓首次深扫 | 1-10 次 | 取决于历史 filing 数，默认云端执行 |
| 单票主动追问 | 0-3 次 | 优先用已入库事件，必要时补摘要 |

### 用户注意力成本

这是最重要的成本。系统每天最多主动展示 5 条事件；没有高优先级事件时只输出一句：

```text
今日无高优先级持仓事件。
```

低优先级事件不主动推送，只在用户主动查询单票时展示。

## 调度频率

### 推荐调度

| 任务 | 频率 | 目标 |
| --- | --- | --- |
| 盘前扫描 | 每个交易日盘前 1 次 | 找到当天和未来 7 天需要关注的事件 |
| 盘后扫描 | 每个交易日盘后 1 次 | 捕捉盘后 SEC filing、公司公告和当日新增事件 |
| 周复盘扫描 | 每周复盘前 1 次 | 补齐本周事件和下周事件 |
| 新持仓扫描 | 买入或持仓新增时触发 | 回看 180-365 天，避免漏掉历史发行/lock-up |
| 单票查询 | 用户主动触发 | 允许更深回看和即时刷新 |

### P1 最小频率

P1 不需要高频。建议：

```text
每日盘后扫描 1 次 + 用户主动查询即时刷新
```

原因：

- SEC filing 和公司公告不是秒级交易信号。
- 用户主要需要防漏，而不是高频新闻流。
- 每日 1 次更容易控制成本、重复提醒和噪音。

P2 再增加盘前扫描：

```text
盘后发现新增事件，盘前提醒未来 7 天事件。
```

### 不建议

- 不建议每 5 分钟刷新闻。
- 不建议对所有观察名单做高频深扫。
- 不建议每天重跑 365 天历史解析。

## 如何保证不重复

去重分四层：source 去重、event 去重、alert 去重、summary 去重。

### 1. Source 去重

同一个来源只保存一次。

去重键：

```text
source_type + accession_number
```

或：

```text
canonical_url + raw_hash
```

例子：

```text
SEC 424B5 0001213900-26-046176
```

如果同一个 URL 原文 hash 没变，不重新解析，不重新调用模型。

### 2. Event 去重

多个来源可以归并到同一个事件。

去重键：

```text
market + symbol + event_type + event_date
```

再加主要来源辅助：

```text
primary_accession_number_or_canonical_url
```

AXTI 例子：

```text
US + AXTI + lockup_expiration + 2026-06-21
```

可以合并：

- SEC 424B5。
- SEC 8-K。
- Business Wire。
- Sahm / Perplexity 媒体标签。

但它们不应该生成 4 条重复提醒。

### 3. Alert 去重和提醒生命周期

同一个事件不应每天重复打扰用户。提醒应按事件生命周期触发，而不是按扫描次数触发。

提醒规则：

```text
event_id + alert_date + channel
```

同一天同渠道只发一次。

### 默认提醒生命周期

对有明确事件日的高优先级事件，默认节奏是：

| 节点 | 是否提醒 | 目的 |
| --- | --- | --- |
| 首次发现，但距离事件日超过 7 天 | 默认不主动提醒 | 先入库，避免过早制造噪音 |
| T-7 到 T-5 | 首次提醒 | 进入可行动观察窗口 |
| T-1 | 二次提醒 | 事件前最后一个准备窗口 |
| T 当天 / 下一交易日 | 当日提醒 | 提醒事件进入交易日 |
| T+1 到 T+3 | 条件提醒 | 只有新增披露、明显波动或用户持仓仍相关时提醒 |

如果事件是在 T-7 窗口内才被发现，立即发首次提醒。

如果事件没有明确事件日，例如 Form 4 / Form 144 披露，则按披露日处理：

```text
披露当天或下一个可推送窗口提醒一次；之后只有新增相关 filing 才提醒。
```

### 跨天再次提醒条件

跨天再次提醒需要满足至少一个条件：

- 事件优先级提升。
- 新增重要 source。
- 事件进入 T-1 或 T 当天窗口。
- 技术面 Agent 后续判断风险升级。
- 用户主动查询。
- 用户选择“继续提醒我”。

### 用户可控提醒状态

每条事件提醒应该允许用户改变后续提醒策略：

| 用户动作 | 后续行为 |
| --- | --- |
| 不再提醒这件事 | 该 `event_id` 不再主动推送，仍可在主动查询和周复盘中出现 |
| 只在有新增时提醒 | 取消 T-1 / T 当天固定提醒，只在新增 source 或风险升级时提醒 |
| 到事件日前一天提醒我 | 保留 T-1 提醒，跳过中间提醒 |
| 继续提醒 | 使用默认生命周期 |
| 这个不重要 | 降低该事件优先级，并记录为反馈 |

P1 可以先用命令式交互实现：

```text
不再提醒 AXTI 这件事
AXTI 只在有新增时提醒
AXTI 到前一天提醒我
```

后续 Web 工作台可以做成按钮。

如果用户已经打开或追问该事件，可以默认降低重复提醒频率，除非用户明确选择继续提醒。

### 4. Summary 去重

同一个事件的可读摘要可以更新，但要标记新增内容。

不要每天输出完整旧摘要，而是输出：

```text
AXTI lock-up 到期事件仍在观察中；今日无新增官方 filing。
```

如果新增来源，则输出：

```text
新增：2026-06-17 Form 4 披露内部人卖出。
```

## 优先级规则

### 高优先级

满足任一条件：

- 当前持仓命中。
- 事件类型为减持、拟减持、lock-up 到期、增发、重大资产/监管事项。
- 事件日期在未来 7 天或过去 3 天。
- 事件规模较大，或者媒体/市场已经明显关注。
- 与近期大幅涨跌、放量、跳空、破位等盘面变化同向出现。

### 中优先级

满足任一条件：

- 关注名单命中，但非当前持仓。
- 财报日、会议、普通 8-K、普通公司新闻稿。
- 事件影响不确定，需要用户决定是否继续研究。

### 低优先级

默认不主动推送，只在单票查询中展示：

- 普通转载新闻。
- 无新增事实的短讯。
- 与持仓关系弱的行业新闻。

## 技术面 Agent 边界

本 PRD 不展开技术面 Agent 设计，但需要为它预留接口。

事件雷达负责回答：

```text
发生了什么？来源是什么？和我的持仓有什么关系？
```

技术面 / 交易影响评估 Agent 负责回答：

```text
这个事件在当前成交量、流通股、K线和趋势状态下，可能有多大冲击？
```

事件雷达需要向技术面 Agent 提供：

- 事件类型。
- 事件日期。
- 事件股数或金额。
- 官方和媒体置信度。
- 当前是否持仓。

技术面 Agent 返回：

- 供应冲击比例。
- 流动性压力。
- 技术脆弱度。
- 关键观察位。
- 高/中/低事件冲击评级。

## 成功标准

### 功能成功

- 当前持仓中出现 Form 4 / Form 144 / 424B5 / 8-K 时，系统能在 24 小时内识别。
- AXTI 类 lock-up 到期事件可以从官方文件和媒体标签中合成事件卡。
- 事件卡能给出来源链接和置信度。
- 重复新闻不会反复推送。

### 产品成功

- 用户每天只需要看 0-5 条持仓相关事件。
- 用户能快速判断“今天有没有值得处理的持仓风险”。
- 周复盘能解释本周重要持仓波动背后的事件候选。
- 系统帮助用户少漏掉关键公告，而不是增加信息焦虑。

## 风险和开放问题

- 媒体事件标签可能错误，需要官方文件校验。
- SEC 文件格式多样，lock-up 条款需要文本抽取和人工校验兜底。
- 不同市场对“解禁”“lock-up”“限售”定义不同，需要按市场单独建规则。
- 富途 App 内部事件源不一定开放，不能把富途体验等同于 API 能力。
- 技术面冲击评估需要独立 PRD，避免本模块过早变成交易建议系统。

## P1 实施切片

### Slice 1：SEC 持仓事件探针

- 输入当前美股持仓 ticker。
- ticker -> CIK。
- 拉取最近 30 天 SEC submissions。
- 识别 `4`、`144`、`8-K`、`424B5`、`S-3`。
- 输出命令行事件列表。

### Slice 2：AXTI lock-up 样例解析

- 针对 424B5 / 8-K 抽取发行股数、发行价、lock-up 期限。
- 计算事件日和下一交易日。
- 生成结构化事件卡。

### Slice 3：事件入库和去重

- 新增 `portfolio_events` 或复用 source facts 体系。
- 按 `symbol + event_type + event_date + canonical_source` 去重。
- 保存来源、证据、推导字段和置信度。

### Slice 4：钉钉/命令入口

- 新增 `持仓事件` / `AXTI 事件`。
- 默认只读，不写用户心得。
- 输出高优先级事件卡。

### Slice 5：周复盘接入

- `weekly_review` context 增加 `events`。
- 高光/炸裂时刻中引用事件候选。
- 模型提示词明确不能把事件相关性写成确定因果。
