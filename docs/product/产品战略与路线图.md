# Product Strategy And Roadmap

## Product Positioning

InvestmentKnowledge is not a generic investment notebook and not an automatic trading system. Its long-term positioning is:

> A personal operating system for investment research, review, and memory.

The system should help the user accumulate investment experience over many years by connecting real holdings, investment journals, stock research, user insights, review reports, and later validation into a traceable and evolving personal investment knowledge system.

## Product Philosophy

The user's core philosophy:

> Investing is a long practice of accumulation. The user wants to stay in the market for a long time, continuously review decisions, preserve experience, and improve judgment so accumulated experience becomes a durable advantage.

The product goal is not to provide more daily information. It is to help the user form stronger long-term judgment.

## North-Star Metric

Phase-one north-star metric:

> Complete one high-quality, traceable, knowledge-preserving investment review every week.

Input metrics:

- Number of account snapshots saved each week.
- Number of raw user insights recorded each week.
- Number of candidate insights generated each week.
- Number of candidate insights confirmed or rejected each week.
- Number of historical views referenced each week.

Quality metrics:

- Whether the review explains major profit and loss sources.
- Whether it identifies portfolio risk and attention cost.
- Whether it references historical judgments.
- Whether it preserves new candidate insights.
- Whether the user wants to return the next week.

## User Journey

### Daily Capture

The user can record at any time through DingTalk, CLI, or another entrypoint:

- Investment ideas.
- Market observations.
- Emotional reactions.
- Trade rationale.
- Historical notes.
- Stock or sector questions.

The system should preserve the original text by default. System-inferred views go to candidates and do not become formal user insights directly.

### Lightweight Daily Automation

Each day, the system should:

- Save account snapshots.
- Save holding snapshots.
- Mark important profit/loss changes.
- Collect events that may need review.
- Avoid generating long reports by default.

The daily layer should be low-disturbance and high-retention.

### Weekly Formal Review

Each week, the system should generate a formal review covering:

- Weekly return overview.
- Main contributors and detractors.
- Holdings, currencies, markets, and theme exposure.
- Concentration and crowded-trade risk.
- What went right, wrong, missed, or impulsive.
- Historical view validation or falsification.
- New candidate insights.
- Three to five things to watch next week.

Weekly review is the core phase-one product experience.

### Long-Term Recall

The user should be able to return to any point in time and inspect:

- Holdings at that time.
- Original notes at that time.
- Market judgments at that time.
- Whether those judgments were later validated.
- Whether today's view conflicts with historical views.

## Product Modules

### 1. Investment Journal Library

Goal: preserve the user's long-term raw notes and ideas.

Key capabilities:

- Import Markdown, text, chat records, and document exports.
- Segment by date, source, and theme.
- Preserve original text without replacing it by summaries.
- Extract stock, sector, portfolio, and strategy targets.
- Generate candidate insights.

### 2. Weekly Review

Goal: create a stable investment practice ritual.

Key capabilities:

- Read account and holding snapshots automatically.
- Calculate returns, contributors, detractors, and exposures.
- Reference this week's new notes and insights.
- Reference and validate historical views.
- Generate candidate insights and next-week watch items.

### 3. Decision Cards

Goal: turn a deep evidence layer into a first-glance decision surface.

Default display:

- One-sentence judgment.
- Core drivers.
- Core risks.
- Watch items.
- Data freshness.
- Source and audit status.

Full sources, knowledge items, audit records, and drafts remain available in the evidence layer when expanded.

### 4. Historical View Validation

Goal: help the user see how judgment changes over time.

Key capabilities:

- Record when a view was formed and the market context around it.
- Identify whether later facts validated the view.
- Detect conflicts between current analysis and historical preferences.
- Build a long-term profile of the user's investment style.

### 5. Research Job Pipeline

Goal: continuously complete the holdings graph and stock research base.

Key capabilities:

- Generate research jobs for holdings.
- Show job status, failure reason, and audit status.
- Show summaries by default.
- Put confirmation-needed output into an explicit review queue.

## Roadmap

### P0: Product Foundation

- Establish product documentation.
- Define north-star metric and product principles.
- Stabilize the Product Agent protocol.
- Separate product direction from technical direction.

### P1: Weekly Review MVP

- Save daily account snapshots automatically.
- Generate formal weekly review Markdown.
- Support a weekly-review command.
- Store the review report in the database or artifact store.
- Generate candidate insights from the review.

### P2: Investment Journal Import

- Import historical journal files.
- Archive original text.
- Segment by date.
- Generate candidate insights.
- Support user confirmation, rejection, and merge.

### P3: Decision Cards

- Use Level 1 decision cards as the default stock display.
- Show slim research-job summaries by default.
- Support explicit evidence-layer expansion.

### P4: Long-Term Memory And Validation

- Retrieve historical views.
- Detect conflicts.
- Mark views as validated or falsified.
- Build a user investment-style profile.

## Product Principles

- Always preserve original text.
- Separate facts, user views, and model inference.
- Only user-confirmed views become formal insights.
- Default displays should serve decisions, not dump material.
- The evidence layer must remain traceable.
- Weekly review has priority over daily long reports.
- The product should be able to run for ten years, not just answer one question.
