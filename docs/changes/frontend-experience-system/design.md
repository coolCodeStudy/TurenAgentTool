# Frontend Experience System Design

## Approach

Use this package as the first repo-native change-package trial. The first phase is inventory and coordination, not implementation. The coordinator should define the current surface map, identify the smallest coherent first slice, and route implementation only after Product/Frontend and Engineering have an explicit plan.

The current application should stay server-rendered for the first implementation slice. A new frontend framework or build pipeline is not justified yet because the active pages are still small, Python-owned, and operationally tied to the existing `weekly-review-web` and `command-api` services. The first slice should instead create a shared app shell/navigation/component contract that can be used by the existing Python renderers.

## Risks

Navigation risks:

- `/weekly-review` presents module-like nav items such as trade review and research queue that are not distinct pages, while `/command` has no global navigation at all.
- `/command` can run Weekly Review commands but does not guide the user to the richer Weekly Review page.
- Daily Market Brief is mentioned as pending in planning docs, but no product package or route exists; adding a nav item now would create a false affordance.

Layout and responsive risks:

- Weekly Review uses a 232px left sidebar, main content, and 220px right aside; Command Workbench uses a separate main-plus-340px-aside layout. The breakpoints and density rules differ.
- Both pages rely on large inline tables and generated content. Weekly Review uses horizontal table overflow on mobile, but the dense control bar, token field, and long status text still need mobile verification before a user-facing release.
- Command Workbench collapses its aside below the main content on narrower screens, which can push action discovery far below the command input.

Component and code ownership risks:

- Each page defines its own CSS variables, button styles, notices, chips, cards, and grid rules inline in Python string renderers.
- Result-card rendering, source-status cards, attribution cards, and notices are page-local patterns with no shared naming or acceptance rules.
- Because `/command` is served by both `command-api` and `weekly-review-web`, visual changes must verify both route owners even when the public URL uses only `weekly-review-web`.

Accessibility risks:

- Primary controls mostly use native buttons/inputs and some ARIA labels, but the pages do not yet have an explicit shared focus style, skip link, landmark policy, or live-region policy.
- Several generated buttons use inline `onclick` handlers and dynamic `innerHTML`; keyboard focus after preview/run/update is not managed.
- Status and error messages are visually prominent, but only part of Weekly Review uses `aria-live`; Command Workbench result updates are not announced consistently.
- Bilingual UI copy is inconsistent: `/command` is primarily English with Chinese examples, while `/weekly-review` is primarily Chinese.

First implementation slice recommendation:

- Build a shared server-rendered app shell and primary navigation contract, then apply it to both `/weekly-review` and `/command` in one bounded slice if Product accepts a two-surface release gate.
- The shell should include a stable brand/header area, primary nav entries for active pages only (`Weekly Review`, `Command Workbench`), a disabled or omitted Daily Market Brief entry until its PRD exists, shared design tokens, shared notice/button/card class names, a basic skip link/focus style, and consistent token-field placement/copy.
- Keep all existing API contracts, command parsing, weekly-review generation, candidate-insight behavior, and localStorage token keys unchanged.
- Non-goals for the first slice: no new frontend framework, no Daily Market Brief implementation, no result-card semantic redesign, no auth/token behavior change, no Weekly Review data/model changes, no user acceptance marking.

If Product wants a lower-risk first slice, the fallback is to implement the shared shell in Weekly Review first and only add a visible link to the existing `/command` route. That avoids changing `/command` rendering in the same release, but it proves less of the shared system and leaves the Command Workbench island in place until the second slice.

## Reviewer Gates

- Frontend Experience Reviewer: applied for this inventory by self-review. Result: pass for planning, with required follow-up that the first implementation PRD/technical plan includes explicit desktop/mobile screenshots and keyboard/accessibility checks.
- Release Reviewer: not required for this inventory because no live surface changes are made. Required for the recommended first implementation slice if it updates both `/weekly-review` and `/command`.
- Acceptance Reviewer: not required for this inventory. Required after a deployed user-facing frontend slice exists.
- Security/Access Reviewer: not required for this inventory or the recommended slice as long as token storage, auth headers, private routes, and secret handling remain unchanged.
